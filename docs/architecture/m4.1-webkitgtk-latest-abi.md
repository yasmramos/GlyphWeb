# WebKitGTK ABI Policy: Latest First (M4.1)

Date: 2026-10-30 — Status: **Accepted**

## Decision

GlyphWeb always targets the **latest stable WebKitGTK release line**. As of
October 2026 that is the **2.50.x series**, whose modern ABI is
`libwebkitgtk-6.0.so` (GTK 4 + libsoup 3). Older families are supported only
as runtime fallbacks, never as the primary target:

| Priority | SONAME family        | Toolkit / HTTP stack | Upstream status            |
|----------|----------------------|----------------------|----------------------------|
| 1        | `webkitgtk-6.0`      | GTK 4 / libsoup 3    | Current (2.40+, incl. 2.50)|
| 2        | `webkit2gtk-4.1`     | GTK 3 / libsoup 3    | Deprecated                 |
| 3        | `webkit2gtk-4.0`     | GTK 3 / libsoup 2    | Deprecated / EOL           |
| 4        | `webkit2gtk-3.0`     | GTK 3 / libsoup 2    | EOL                        |

## Why

- **Security & features:** WebKitGTK 2.50 ships the current JIT sandbox, DMA-BUF
  zero-copy scanout and media stack; older ABIs stop receiving upstream fixes.
- **One bridge, many ABIs:** every `webkit_*` symbol bound by
  `NativeWebKit` exists with identical signatures across 6.0 and 4.1, so the
  JNI companion (`libglyphwebkit.so`) dlopens whichever library the probe
  resolved. The GTK-version deltas that *do* exist (`gtk_init_check` vs
  `gtk_init`, implicit visibility, `gtk_container_add` vs
  `gtk_widget_set_parent`) are absorbed inside the C bridge, not in Java.
- **GC/allocation impact:** none. The policy only changes which `.so` gets
  `dlopen`ed; hot-path call shape is identical.

## Implementation surface

- `NativeLibraryProbe.CANDIDATES` — newest-first SONAME list; also honours
  `-Dglyph.webkit.library.path=<abs>` to pin a custom build (CI containers,
  locally compiled nightlies), and falls back to parsing
  `webkitgtk-6.0.pc` when standard dirs miss it.
- `NativeLibraryProbe.gtkMajorForFamily()` — maps family → GTK major (6.0→4,
  everything else→3); feeds `WebKitCapabilities.gtkMajor()`.
- `WebKitRuntime.buildCapabilities()` — SANDBOX + HARDWARE_ACCELERATION are
  advertised for 6.0 and 4.1/4.0; the error message now names
  `libwebkitgtk-6.0-dev` as the recommended package.
- Tests: `NativeLibraryProbeTest` asserts the override path, the GTK-major
  mapping, and that when both ABIs are installed the probe must pick 6.0.

## Verification on this machine

Debian bookworm's repository carries WebKitGTK **2.50.6** for both
`libwebkitgtk-6.0-dev` and `libwebkit2gtk-4.1-dev` candidates — i.e. even the
legacy SONAME wraps the latest engine. Full suite green (39 tests) after the
ABI-policy change.
